## 一、结论（冻结范围 + 修改门禁）

### 1.1 冻结范围

本合同冻结 `ladder_day__raw → dates[] → boards[] → stocks[]` 展平为 **16 列 TSV** 的完整字段清单，用于 P1/P3 结构指标计算、高标观察池生成、历史回测批量导入。所有消费方（脚本 / 手动表格 / 可视化）**只认本合同 16 列**，不读原始 JSON 其他字段。

### 1.2 修改门禁（3 天回归规则）

> **改列 = 增列 / 删列 / 改类型 / 改取值口径，4 类全部算改列。**

| 门禁等级 | 条件 | 流程 |
|---------|------|------|
| 🟢 紧急修复 | 某列在 8/10 真实样例中出现 null/空/取值越界 ≥5% | 当日提交 PR → 次日回归 1 天 → 第 3 天生效 |
| 🟡 常规增删 | 新增指标需要新列 / 某列确认为无用 | 提案 → 连续 3 个交易日回归（8/11, 8/12, 8/13）→ 第 4 天生效 |
| 🔴 口径变更 | 如 `trading_amount` 从「元」改「万元」、`turnover_rate` 从「%值」改「小数」 | 提案 → 3 天回归 + 全量历史 TSV 重刷验证 → 第 7 天生效 |

**冻结声明**：本合同自 2026-08-11 起生效。任何改列操作必须先过 **至少 3 个连续交易日** 的回归验证（对比旧口径与新口径的 P1 6 栏 / P3 5 栏输出差异 ≤1 档），未过回归不得上线。违反门禁造成的下游脚本崩溃 / 指标失真 = 回滚到上一版合同。

## 三、操作步骤（日常使用 + 改列流程）

### 3.1 日常：从 raw JSON → 16 列 TSV（标准导出流程）

1. **输入定位**：找到当日 `ladder_day_min__YYYYMMDD.json`（或 `ladder_day_raw__YYYYMMDD.json`）
2. **展平循环**：
   - 外层：`for day in dates` → 取 `day.date` 写入 `trade_date`
   - 中层：`for board in day.boards` → 取 `board.level` 写入 `board_level`
   - 内层：`for stock in board.stocks` → 按上表 16 列逐一映射取值
3. **空值兜底**（按上表第 5 列规则）：
   - `primary_theme` 缺 → 写 `UNKNOWN`
   - `limit_up_type` 缺 → 写 `OTHER`
   - `open_num` null/缺 → TSV 空串
   - `trading_amount`/`order_amount` 缺 → 写 `0`
   - `turnover_rate` null → TSV 空串
4. **TSV 写盘**：文件名 `ladder_16col__YYYYMMDD.tsv`，header 必须严格等于上表「列名」顺序
5. **自检验**：
   - 行数 = 当日 `totalStocks`（与 `dates[0].totalStocks` 对得上，±2 内允许）
   - `level` 与 `board_level` 不一致的行数 = 0（或 ≤1 手动检查）
   - 16 列 tab 分隔数正确（每行 15 个 tab）

### 3.2 改列提案流程（3 天回归门禁）

1. **提案页**：在旧仓 90 区新建 `ladder_16col_proposal__YYYYMMDD.md`，写明：
   - 改列类型（增/删/改类型/改口径）
   - 动机（哪个 P1/P3 栏位卡壳了 / 哪列连续 3 天空值率 >80%）
   - 新旧口径对比样例（至少用 8/10 真实数据跑一组）
2. **Day 1 回归（提案当日）**：
   - 用新口径重刷 8/10 TSV → 计算 P1 6 栏 / P3 5 栏
   - 与旧口径输出对比 → 记录差异（允许「结构-资金矩阵」情绪档偏差 1 档，其他栏位必须一致）
3. **Day 2 + Day 3 回归（连续 2 个实盘日）**：
   - 当日收盘后，新 / 旧口径各跑一份 → 对比 P1/P3 输出
   - 3 天累计差异：情绪档偏差 ≤1 档 × 3 天，无连续 2 天偏差
4. **生效**：
   - 附 3 天回归对比表 → 更新本合同「二、字段表格」
   - 版本号 +1（如 `v1.1`），在文末追加「变更历史」小节
   - 通知所有下游脚本维护人更新 TSV reader

### 3.3 违规应急（发现某列口径错了但已被消费）

1. 当日立即 **回滚到上一版合同** 重新导出 TSV
2. 在 `batch_datasource_gap__20260811/` 下记 `ladder_16col_incident__YYYYMMDD.md`
3. 下次走改列流程时必须把本次事故作为「回归必测项」
