# A5 G5_G6 多家AI正式发包稿

更新时间：2026-07-16

## 用途

- 这份发包稿只负责把 `A5` 当前 `G5 / G6` 的硬边界讨论，压成可直接复制发送的标准文本。
- 当前不是开放式闲聊。
- 当前是：
  - 可发包
  - 可回收
  - 可裁决

## 使用方式

- 发给外部模型时，不要自由改写核心边界。
- 若需要差异化提问：
  - 只改“视角偏置”
  - 不改 `TASK / BACKGROUND / KNOWN_CONSTRAINTS / DISCUSSION_SCOPE`
- 默认至少发给 `3` 类视角：
  - 架构/系统
  - 执行/落地
  - 风险/反例

## 标准发包稿

```text
你现在参与的是一个多AI讨论，不是自由闲聊。

TASK:
- 讨论 A5 当前在“对象卡可读样例层”之后，下一手应如何处理 G5（组合层关键上游闭合）与 G6（数据粒度边界闭合），并给出 2-4 个不同方案对照。

BACKGROUND:
- 当前项目主线已经从 req 级字段整理，推进到：
  - A5 最小对象卡草案
  - A5 字段真实来源状态表
  - A5 runtime 对接边界页
  - A5 最小样本实例卡
  - A5 正式对象卡模板
  - A5 实现前冻结门槛页
  - A5 实现阻塞项拆解表
- 当前已经通过：
  - G1 对象卡骨架冻结
  - G2 字段来源状态冻结
  - G3 runtime 边界冻结
  - G4 最小样本可读性冻结
  - G7 实现前验证口径冻结
- 当前仍未通过：
  - G5 组合层关键上游闭合
  - G6 数据粒度边界闭合

KNOWN_CONSTRAINTS:
- 当前阶段仍禁止：
  - runtime 新开发
  - 默认执行逻辑扩展
  - 回测自动化
  - 大范围 second-hop 深扫
- 不允许把：
  - proxy
  - rules_engine_derivable
  - future_only
  误写成 runtime 已支持
- 不允许为了推进感，把：
  - target_weight
  - portfolio_tracking_error
  - minute / level2
  直接升格为默认实现输入
- 若缺证据，必须显式写 NEED_EVIDENCE

CURRENT BLOCKERS:
- alpha_score = proxy
- covariance_model_id = future_only
- target_weight = future_only
- portfolio_tracking_error = future_only
- minute_data_runtime_status = sample_only_with_provenance
- level2_runtime_status = future_only

DISCUSSION_SCOPE:
- 本轮允许讨论：
  - G5 最稳的清障顺序
  - G6 是否应继续冻结
  - alpha_score 应保留代理合同，还是追求唯一主源
  - covariance / target_weight / tracking_error 是否值得进入实现前准备
  - 数据粒度边界是否应继续维持 daily_only
- 本轮不要展开：
  - 具体代码实现
  - 优化器编码选型
  - 分钟策略开发
  - Level-2 扩新采购与新系统扩张

FREE_GUESS_RANGE:
- 允许合理推测：
  - 哪条清障路径最稳
  - 哪条路径最容易返工
  - 哪些字段适合继续停在合同层
  - 哪些字段值得进入实现前口径
- 以下内容若无硬证据必须写 NEED_EVIDENCE：
  - alpha_score 是否存在唯一稳定主源
  - 协方差模型的正式可实现口径
  - target_weight 的最小求解链
  - 分钟 formal raw catalog 是否已可用

CANDIDATE MODES:
1. 保守冻结型
- G6 继续冻结
- 只处理 G5 的合同层清障
- alpha_score 允许保留代理合同

2. 分阶段解锁型
- 先把 alpha_score 代理合同正式化
- 再决定是否为 covariance / target_weight / tracking_error 建实现前入口
- G6 暂时保持冻结

3. 平衡推进型
- G5 进入实现前口径收束
- G6 只保留 daily_only
- 明确 minute / Level-2 长期观察位

4. 激进推进型
- 同时追 G5 + G6
- 尝试把组合层上游与分钟级边界一起前推

EXPECTED_OUTPUT:
- 请至少给出 2-4 个不同方案，不允许只给唯一答案
- 每个方案至少说明：
  - 方案名
  - 核心思路
  - 适用条件
  - 优点
  - 缺点
  - 风险
  - NEED_EVIDENCE
  - 为什么适合当前项目
- 最后必须补：
  - 你最推荐的方案
  - 不推荐其它方案的原因
  - 当前最小下一步

OUTPUT CONTRACT:
1. 结论摘要
2. 方案对比（至少2个）
3. 最推荐方案
4. 当前最小下一步
```

## 视角偏置版

### 架构/系统视角

```text
额外要求：
- 请优先从对象卡、合同层、实现前准入关系来判断。
- 请回答：哪种方案最不容易把合同层边界写穿。
```

### 执行/落地视角

```text
额外要求：
- 请优先从清障顺序、返工概率、最小落地成本来判断。
- 请回答：哪种方案最容易形成“可继续推进但不越界”的最小下一步。
```

### 风险/反例视角

```text
额外要求：
- 请优先从失败代价、误写风险、假闭合风险来判断。
- 请回答：如果现在选错，哪种路径最容易把 A5 误推进成 runtime ready 幻觉。
```

### 规划/排序视角

```text
额外要求：
- 请优先从阶段顺序和后续主线稳定性来判断。
- 请回答：G5 与 G6 的最稳排序是什么，为什么。
```

## 默认发包顺序

- 第 1 轮：
  - 发给 `架构/系统视角`
  - 发给 `执行/落地视角`
  - 发给 `风险/反例视角`
- 第 2 轮：
  - 若分歧明显，再加发 `规划/排序视角`
