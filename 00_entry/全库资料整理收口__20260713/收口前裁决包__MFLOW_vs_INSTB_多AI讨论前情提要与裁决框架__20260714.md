# 收口前裁决包 MFLOW vs INSTB 多AI讨论前情提要与裁决框架

更新时间：2026-07-14

## 用途

- 这份文档只负责为 `MFLOW` 与 `INSTB` 的下一轮多 AI 讨论准备标准前情提要与裁决框架。
- 当前不是直接拍板“二选一”，而是先把：
  - 讨论什么
  - 不讨论什么
  - 哪些允许推测
  - 哪些必须写 `NEED_EVIDENCE`
  固定下来。

## 当前任务

- 在不打断首批补采主线的前提下，判断 `MFLOW` 与 `INSTB` 谁更适合作为“第二批观察里优先补的一条线”。

## 前情提要

- 当前项目主线仍停留在：
  - 纯资料整理收口
  - 首批补采闭环
  - 方案B 进入前裁决
- 当前已形成正式资料入口的参考系统主要是：
  - `NFTRADEZ`
  - `Smile_SMC交易系统2_0`
  - `TK外汇`
- 当前首批补采对象是：
  - `Batch9 N02`
  - `Batch9 N01`
  - `YTC`
  - `CHZL_BSD`
- 当前第二批观察里，真正需要二选一预裁决的是：
  - `MFLOW`
  - `INSTB`
- `ATRATIO`
  - 当前继续冻结在 `future_only`

## 已知约束

- 当前阶段仍然只做资料整理，不进入：
  - runtime 新开发
  - 默认执行逻辑扩展
  - 回测与自动化实现
- `MFLOW / INSTB` 当前统一推荐深度是：
  - `样本合同候选`
- 不允许因为“概念听起来更强”就直接升格为首批补采。
- 不允许把缺证据的推测写成已验证事实。
- 若 provider 可得性、样本成本或解释收益不清楚，必须写：
  - `NEED_EVIDENCE`

## 本轮讨论边界

- 本轮允许讨论：
  - 谁更值得先做 provider 审计
  - 谁更可能更快拿到最小样本
  - 谁更贴近当前仓内对象卡和解释链
  - 谁更适合做第二批观察的优先入口
- 本轮明确不讨论：
  - 具体实现代码
  - 指标公式正式实现
  - 默认执行链接线
  - 新 runtime 架构展开

## 允许自由推测范围

- 允许合理推测：
  - `MFLOW` 与 `INSTB` 在样本可得性、解释收益、维护成本上的相对差异
  - 哪类 provider 依赖更可能成为阻塞点
  - 哪条线更适合先做“审计页”而不是直接开批次
- 必须写 `NEED_EVIDENCE` 的内容：
  - 具体 provider 名单与真实可用性
  - 历史样本覆盖区间
  - 字段是否稳定
  - 是否存在可接受的替代源
  - 与现有对象卡的实际绑定强度

## 期望输出

- 每个模型至少给出 `2-4` 个方案，不允许只给唯一答案。
- 每个方案至少说明：
  - 方案名
  - 核心思路
  - 适用条件
  - 优点
  - 缺点
  - 风险
  - `NEED_EVIDENCE`
  - 为什么适合当前项目
- 最后必须补：
  - 最推荐方案
  - 不推荐其他方案的原因
  - 当前最小下一步

## 建议评分轴

| 评分轴 | 问题 | 说明 |
|---|---|---|
| 样本可得性 | 谁更容易拿到最小可审计样本 | 优先看 provider friction，而不是概念吸引力 |
| 闭环距离 | 谁更接近现有对象卡/解释链 | 优先看能否更快形成仓内闭环 |
| 解释收益 | 谁对后续 explain layer 更有直接帮助 | 不是看“高级感”，而是看可落地解释价值 |
| 维护成本 | 谁后续更不容易被外部依赖拖垮 | 外部依赖越重，越要谨慎 |
| 失败代价 | 选错后谁的沉没成本更高 | 先选失败代价更低的一方更稳 |

## 预设方案骨架

### 方案A：先审 `MFLOW`

- 核心思路：
  - 先把 `MFLOW` 做成 provider 与样本可得性审计页，再判断是否值得独立开批次。

### 方案B：先审 `INSTB`

- 核心思路：
  - 先把 `INSTB` 做成 provider 与样本可得性审计页，再判断是否值得独立开批次。

### 方案C：双审计后再裁决

- 核心思路：
  - `MFLOW` 与 `INSTB` 都先停在“审计页”层，不急着定唯一优先者，再用样本成本和闭环距离做第二跳裁决。

### 方案D：继续延后

- 核心思路：
  - 若首批补采硬门槛尚未关闭，则 `MFLOW / INSTB` 继续停在第二批观察池，不立即重启。

## 主负责人裁决框架

- 最终裁决不是看“哪个名字更像高级系统”，而是按以下顺序收口：
  - 样本可得性
  - 闭环距离
  - 解释收益
  - 维护成本
  - 失败代价
- 若两个对象都缺硬证据：
  - 不强行二选一
  - 允许先采纳 `方案C` 或 `方案D`
- 若其中一条线出现明显更低的 provider friction，且更贴近现有解释链：
  - 才允许把它升为第二批观察优先项

## 本轮多AI复核摘要

- 架构 / explain-chain 视角：
  - 偏 `MFLOW`
  - 原因是它更贴近当前解释链、过滤层和现有对象互锁关系
- 数据可得性 / 审计闭环视角：
  - 偏 `MFLOW`
  - 原因是仓内已经存在更接近 `moneyflow` 的运行脚手架与样本合同痕迹
- 失败成本 / 维护风险视角：
  - 偏 `INSTB`
  - 原因是它更像方法层背景信息，失败时对主线扰动更小

## 当前预裁决

- 当前不是“完全没有方向”。
- 当前三路复核结果更接近：
  - `2` 路偏 `MFLOW`
  - `1` 路偏 `INSTB`
- 主负责人当前预裁决：
  - 先审 `MFLOW`
  - `INSTB` 暂不升格，只保留在第二批观察池
- 但这个裁决的含义是：
  - 先做 `MFLOW` 的 provider / 字段映射 / divergence 派生审计
  - 不是直接把 `MFLOW` 提升为首批补采
  - 也不是把 `INSTB` 判成无价值
- 当前采用的具体口径更接近：
  - `方案A`
  - 但保留 `方案C` 的保守边界
  - 即 `MFLOW` 先审，`INSTB` 继续观察，不立刻开第二个新批次
