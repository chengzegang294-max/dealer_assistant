# A5 信息直播间稳定抓取｜多AI讨论前情提要与发包稿

更新时间：2026-08-01

## 一、当前任务

- 讨论的问题不是“这个站能不能看”。
- 当前唯一问题是：
  - 在登录态历史记录页里，如何把当前屏幕可见的消息稳定导出成结构化 JSON。

## 二、前情提要

- 当前项目已完成：
  - 信息直播间房间列表抽取
  - 房间评分与置顶候选
  - 多批当前页导出样例
  - 25个直播间带截图对照

- 当前已确认：
  - `room_anchor` 基本可用
  - 真正不稳定的是：
    - `display_date`
    - `display_time`
    - `topic_anchor`
    - `excerpt`
    - `visible_messages[0]`

- 当前已发生的典型错误包括：
  1. 抓到同房间但不是当前屏幕里的旧消息
  2. 把 `倒序观看历史记录 / 历史记录 / 搜索直播间消息 / 时间 / 选择日期`
     这种 UI 文本误当成第一条消息
  3. 页面有 `socket_disconnect / login_timeout / websocket failed`
     等不稳定迹象
  4. 用户肉眼看到的是 `2026/07/30`、`2026/07/31` 这批消息，
     JSON 却抓成 `2026/07/22`、`2026/07/27` 之类旧内容

## 三、已知约束

- 当前站点是：
  - `SPA + 登录态 + 历史记录页 + 左列表右内容`
- 当前优先目标不是全自动无人值守，而是：
  - `稳定导出当前屏幕可见内容`
- 不默认假设公开 API。
- 不把随机成功当作通过。
- 只要输出与当前视口不一致，就视为未通过。

## 四、本轮讨论边界

- 本轮允许讨论：
  1. DOM 抽取策略是否该继续修
  2. 是否应改成基于几何位置的当前视口卡片提取
  3. 是否需要换浏览器、换打开方式、固定等待条件
  4. 是否该升级到浏览器自动化/扩展方案

- 本轮不要展开：
  1. 房间价值评分
  2. 金融有效性
  3. 图片 OCR 的长期方案
  4. 全自动量产架构

## 五、允许自由推测范围

- 可推测：
  - 当前页面为何会把旧 DOM / UI 文本 / 当前消息混在一起
  - 哪种抓取策略在这类 SPA 历史页更稳
  - 哪些浏览器行为会污染抓取结果

- 必须写 `NEED_EVIDENCE` 的部分：
  - 是否存在更稳定的内部接口
  - 某个浏览器一定优于另一个浏览器
  - 某个 websocket 报错一定意味着不可导出

## 六、期望输出

- 请至少给出 `2-4` 个不同方案，并比较：
  - 适用条件
  - 优点
  - 缺点
  - 风险
  - NEED_EVIDENCE

- 最后必须回答：
  1. 继续修 DOM 抽取，还是换路线
  2. 当前最小下一步是什么

## 七、只复制这个文件到外部模型对话框

- 只复制本页中的 `唯一发包文本`
- 不要把其他参考页一起复制过去
