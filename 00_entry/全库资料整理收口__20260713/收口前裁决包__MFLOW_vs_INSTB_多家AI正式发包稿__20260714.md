## 用途

- 这份发包稿只负责把 `MFLOW vs INSTB` 的下一轮多家 AI 讨论，压成可直接复制发送的正式文本。
- 当前不再做 first-hop 预备说明，而是进入：
  - 可发包
  - 可回收
  - 可裁决

## 使用方式

- 发给外部模型时，不要自由改写核心边界。
- 若需要差异化提问：
  - 只改“视角偏置”
  - 不改 `TASK / BACKGROUND / KNOWN_CONSTRAINTS / DISCUSSION_SCOPE`
- 默认至少发给 `3` 类视角：
  - 架构/系统
  - 执行/落地
  - 风险/反例

## 标准发包稿

```text
你现在参与的是一个多AI讨论，不是自由闲聊。

TASK:
- 在不仓促切入方案B的前提下，判断 MFLOW 与 INSTB 谁更适合作为第二批观察里优先继续补的一条线，并给出保守/平衡/激进或等价的多方案对照。

BACKGROUND:
- 当前项目仍处于“纯资料整理收口 + 方案B进入前裁决”阶段。
- 首批补采对象是 Batch9 N02、Batch9 N01、YTC、CHZL_BSD。
- 首批补采硬门槛已经通过外部分钟数据补件闭合，不再被 batch_147 阻塞。
- 当前第二批观察里，真正要比较的是 MFLOW 与 INSTB。
- MFLOW 当前已经补出：
  - provider 与样本可得性审计页
  - 字段映射审计页
  - divergence_score v0 派生审计页
  - 真实样本链与可复现 runner
- INSTB 当前已经补出：
  - provider 与样本可得性审计页
  - 字段合同 / acceptance / runtime dependency 锚点
  - 但尚无真实样本抓取链

KNOWN_CONSTRAINTS:
- 当前阶段仍只做资料整理收口，不进入：
  - 新 runtime 开发
  - 默认执行逻辑扩展
  - 回测与自动化实现
- 不允许把概念偏好直接写成结论。
- 不允许把 proxy 路线误写成已验证真值。
- 若缺证据，必须显式写 NEED_EVIDENCE。
- 当前不允许因为“听起来更高级”就直接把对象升格为首批补采。

DISCUSSION_SCOPE:
- 本轮允许讨论：
  - 谁更值得先作为第二批观察里的优先继续补对象
  - 谁更快形成最小可审计闭环
  - 谁更贴近现有对象卡与解释链
  - 谁的 provider friction 更低
  - 谁的失败代价更低
- 本轮不要展开：
  - 具体代码实现
  - 指标公式正式实现
  - 默认执行链接线
  - 大规模 runtime 架构改造

FREE_GUESS_RANGE:
- 允许合理推测：
  - MFLOW 与 INSTB 在样本可得性、解释收益、维护成本、失败代价上的相对差异
  - 哪条线更适合作为“第二批观察优先入口”
  - 哪条线更适合停在方法层，哪条线更适合继续做 proxy 审计
- 以下内容若无硬证据必须写 NEED_EVIDENCE：
  - 具体 provider 的真实可用性与稳定性
  - 历史样本覆盖区间与抓取成本
  - 字段能否稳定映射
  - 替代源是否足够接近
  - 与现有对象卡/解释链的长期绑定强度

KNOWN_EVIDENCE:
- MFLOW:
  - 已有 Tushare moneyflow + daily 的真实样本链
  - 已有 sample20_q2 跨月样本
  - 已完成字段映射初审
  - 已完成 divergence_score v0 派生审计
  - 当前仍缺 sellord_ratio / open_intent 的强同构字段
- INSTB:
  - 已有字段合同、acceptance、runtime dependency 口径
  - 当前主路线更接近 quarterly_holdings_proxy
  - top_list / Level-2 可作参考，但当前均非主入口
  - 当前尚无真实样本抓取链和可复现 runner

EXPECTED_OUTPUT:
- 请至少给出 3 个不同方案，不允许只给唯一答案。
- 每个方案至少说明：
  - 方案名
  - 核心思路
  - 适用条件
  - 优点
  - 缺点
  - 风险
  - NEED_EVIDENCE
  - 为什么适合当前项目
- 最后必须补：
  - 你最推荐的方案
  - 不推荐其它方案的原因
  - 当前最小下一步

OUTPUT CONTRACT:
1. 结论摘要
2. 方案对比（至少3个）
3. 最推荐方案
4. 当前最小下一步
```

## 视角偏置版

### 架构/系统视角

```text
额外要求：
- 请优先从对象卡、解释链、后续系统耦合关系来判断。
- 请回答：谁更适合作为第二批观察里的“系统级优先入口”。
```

### 执行/落地视角

```text
额外要求：
- 请优先从 provider friction、样本成本、最小闭环速度来判断。
- 请回答：谁更容易在当前仓内形成低成本、可复用、可追溯的最小审计闭环。
```

### 风险/反例视角

```text
额外要求：
- 请优先从失败成本、证据缺口、误判风险来判断。
- 请回答：如果现在选错，哪条线更容易形成沉没成本，为什么。
```

### 规划/排序视角

```text
额外要求：
- 请优先从阶段推进顺序来判断。
- 请回答：在“先收口前裁决，再正式切方案B”的节奏下，最稳排序是什么。
```

## 默认发包顺序

- 第 1 轮：
  - 发给 `架构/系统视角`
  - 发给 `执行/落地视角`
  - 发给 `风险/反例视角`
- 第 2 轮：
  - 若结论分歧明显，再加发 `规划/排序视角`
- 第 3 轮：
  - 主负责人根据回收记录页做统一裁决，不把“票数最多”直接当结论
