# A5 信息直播间稳定抓取｜多AI回包吸收与主负责人裁决

更新时间：2026-08-01

## 一、当前任务

- 当前唯一任务：
  - 让登录态历史记录页的导出结果，稳定等于“当前屏幕可见消息”。

## 二、多AI回包结论吸收

### 1. 关于浏览器 / 打开方式

- 多AI一致判断：
  - 主问题不是 `Edge` 和 `Chrome` 谁更强。
  - 真正问题是：
    - `SPA + 登录态 + WebSocket + 历史页 DOM 缓存`
      共同导致页面状态容易不干净。

- 因此当前第一优先级不是：
  - 盲目换浏览器

- 当前第一优先级应改为：
  1. 固定进入路径
  2. 固定页面状态
  3. 固定导出时机

### 2. 关于 DOM 抽取主链

- 多AI一致判断：
  - 当前提取逻辑仍然太宽。
  - 问题不在于“正则写得不够多”，而在于：
    - 用整块 `contentRoot` 全文拼接切消息
    - 用垂直区间代替真正的同卡片分组
  - 这会把：
    - UI 文本
    - 旧历史消息
    - 当前消息
    一起吞进去。

- 当前正式裁决为：
  - 必须改成：
    `时间标题 + 同卡片容器 + 滚动视口裁剪`
    的联合提取
  - 不再把：
    `整块全文本正则切消息`
    当正式主链

## 三、主负责人裁决

### 当前选什么

- 选：
  - `方案A 为主：几何/结构联合提取`
  - `方案D 为辅：固定操作协议与导出时机`

### 为什么选这个

- 因为当前已证明：
  - `room_anchor` 基本可用
  - 真正不稳的是消息边界
- 继续换浏览器，不能把错误边界自动变对。
- 继续加全文本规则，只会越补越脏。

### 为什么不先选另外几个

- 不先选“换浏览器”：
  - 这只是缓解噪声，不是主解
- 不先选“全自动浏览器自动化”：
  - 当前连最小真值门槛都还没打通，过早自动化只会机械化错误
- 不先选“直接赌内部接口”：
  - 当前还没有足够证据证明历史页接口可稳定复用

## 四、当前正式执行顺序

1. 先冻结人工操作协议：
   - 单标签页
   - 固定浏览器 profile
   - 不刷新
   - 从房间列表点入历史页
   - 日期选定后等待短时间稳定

2. 再收紧脚本主链：
   - 只在当前消息滚动视口内找时间标题
   - 每个时间标题只回收同一卡片祖先下的正文
   - 顶层摘要字段只允许来自第一条真实消息

3. 暂时保留：
   - 全文本切段
   但只作为调试输出，
   不再参与正式字段生成
