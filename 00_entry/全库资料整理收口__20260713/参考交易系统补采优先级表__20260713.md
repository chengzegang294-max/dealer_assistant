# 参考交易系统补采优先级表

更新时间：2026-07-14

## 用途

- 这份表只回答一件事：
  - 当前“最后一轮资料收集”里，参考交易系统和补采线索应该先补什么、后补什么、补到多深为止。
- 当前阶段仍然只做资料整理，不把任何参考系统直接写成默认执行逻辑。

## 多AI讨论前情提要

- 当前已正式落盘并可检索的参考系统主线：
  - `NFTRADEZ`
  - `Smile_SMC交易系统2_0`
  - `TK外汇`
- 当前仍待补的不是“再找更多系统”，而是：
  - 已提到候选系统的补采优先级
  - 每条线应拆到多深
  - 哪些只做映射，哪些值得进入首批补采

## 本轮讨论边界

- 本轮允许讨论：
  - 资料补采顺序
  - 证据缺口顺序
  - 拆包深度
  - 首批/第二批补采分层
- 本轮明确不讨论：
  - 功能接线
  - runtime 新开发
  - 回测与执行逻辑扩展

## 多AI方案对照摘要

- `方案A：参考系统收口优先`
  - 先补 `NFTRADEZ / Smile / TK` 的映射页与资料完备度
  - 优点是最稳
  - 缺点是对后续对象/验证链反哺较弱
- `方案B：Batch9 + 可跑对象双线补采`
  - 先补 `Batch9 N02/N01` 的证据缺口
  - 同步补 `YTC / CHZL_BSD`
  - 优点是最平衡，兼顾资料层和对象层
  - 缺点是需要严格控边界，防止滑到功能开发
- `方案C：外部数据依赖对象优先`
  - 先补 `MFLOW / INSTB / ATRATIO`
  - 优点是补弱项
  - 缺点是 provider 依赖最重、失败率更高

## 主负责人裁决

- 当前采用：
  - `方案B` 为主
  - `方案A` 的最小映射收口为辅
- 裁决原因：
  - `Batch9` 已有最明确的证据缺口清单和重开顺序
  - `YTC / CHZL_BSD` 比 `MFLOW / INSTB / ATRATIO` 更接近“可形成后续闭环”
  - `NFTRADEZ / Smile / TK` 当前更适合继续保持参考系统角色，不抢占首批补采主线

## 收口后新口径

- `MFLOW vs INSTB` 的多家 AI 回收与主负责人裁决已经完成。
- 当前第二批观察内的排序不再是“待讨论”：
  - `MFLOW`
    - 固定为 `第二批观察中的优先审计对象`
    - 只按 `proxy` 边界继续推进
  - `INSTB`
    - 固定为 `观察位`
    - 只保留极小补证位，不反超 `MFLOW`
- `MFLOW` 当前两个最强缺口字段：
  - `mflow_sellord_ratio`
  - `mflow_open_intent`
  已正式定性为：
  - `historical_contract_defined__current_real_source_missing`
  - 也就是保留 `NEED_EVIDENCE`，但不再作为当前先审阻塞
