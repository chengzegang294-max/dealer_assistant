## 这套“效果”想表达什么

- 左侧：图表是主战场，负责给出当前价格行为与关键结构的直观信息。
- 右侧：不是单纯聊天，而是“带状态变量的决策树/问答流 + 可回放的决策轨迹”。
- 最终产物不是一句“做多/做空”，而是：
  - 当前环境状态是什么
  - 当前可用的策略/规则是哪一类
  - 每个结论的依据与未满足的条件是什么
  - 决策过程可回放、可追溯、可复核

## 逐帧文字化（按信息流，不强行逐像素复述）

### 1) 入口界面：图表 + 逻辑树（`1.png`）

- 左侧是行情图表（K线 + 均线/辅助线等），作为视觉证据底座。
- 右侧出现多个“节点卡片”，像树一样从上到下串联，呈现一种问答式流程：
  - 每个节点有提问、分支与选择
  - 节点之间的连线代表“上一结论 -> 下一问题”的依赖关系
- 这说明目标体验不是“把指标丢给你”，而是“把分析过程结构化并可交互”。

### 2) 中间态：状态变量与分支结果被显式打印（`10.png`）

- 右侧变成更偏“结构化日志/决策trace”的呈现：
  - 出现类似 `broad_channel / normal_channel / direction / signal_confidence / market_phase` 的变量名
  - 这些变量像是对市场的“可枚举状态描述”，用于驱动后续分支
- 重要启发点：
  - 系统把“判断”拆成可落盘、可复核的状态变量
  - 决策不是凭感觉，而是由一组状态变量触发不同的策略/规则路径

### 3) 深一层：规则/策略表 + gate trace（`20.png`）

- 右侧内容进一步呈现“规则库/策略表 + 决策轨迹”导向：
  - 在同一屏幕里既有状态摘要，也有规则触发/否决信息
  - 体现出一种 `gate_trace` 风格：每一步为什么通过/为什么拒绝
- 重要启发点：
  - 未来我们的解释层需要的不只是结果字段，还要有“过程证据”（decision trace）
  - 规则表与状态变量需要能对齐：规则用到哪些变量、阈值来自哪里、证据是什么

### 4) 收口形态：策略/规则清单 + 问题树索引（`27.png`）

- 上半区像“策略/规则清单表格”（带编号、名称、描述等），更接近“可检索的规则库”。
- 下半区像“问题树/节点索引”，把整套问答拆成可复用的问题集合（每个问题对应一个分支点）。
- 重要启发点：
  - UI 的终点不是一个信号，而是一个“可维护的知识库结构”：
    - 规则表（可版本化、可审计）
    - 问题树（可复用、可重排）
    - 决策轨迹（可复盘）

## 映射到本仓库（主线对齐）

- 这套“效果”的信息流，与我们当前 Batch9 的推进顺序同构：
  - 输入层：OHLC + session/calendar +（研究侧）事件数据
  - 环境层：`N02`（session/OR）
  - 状态层：`N01`（ATR/percentile/squeeze）
  - 结构层：`N03`（结构/突破质量，仍保持条件型候选）
  - 解释层：把 N02/N01/N03 的输出组装成“状态变量 + gate trace + 规则表”

## 当前可落地的“最小复刻目标”（不越界）

- 不追求复制外部 SMC 细节名词，而是复刻这三类工程能力：
  - 状态变量可落盘（N02/N01 已在做）
  - 决策过程可追溯（下一阶段新增 decision trace 的落盘样式）
  - 规则库可检索（研究侧 rule table / decision table 的格式先定出来）
