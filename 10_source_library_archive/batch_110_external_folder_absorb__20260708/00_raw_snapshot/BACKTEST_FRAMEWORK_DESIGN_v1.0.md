# 回测框架设计文档（纯架构，零代码）

> 版本：v1.0 | 状态：架构设计阶段 | 约束：不编码，仅定义规范、接口、流程与验收标准  
> 覆盖对象：12 张已冻结对象卡（结构 4 + 执行 7 + 风控 2 + 选股 4）  
> 目标：将离散对象卡从"卡片堆"转化为"有执行顺序的系统"

---

## 1. 文档定位与阅读说明

### 1.1 为什么需要这份文档

当前仓库有 12 张字段冻结的对象卡，但它们之间缺少**执行层面的连接规范**：
- 每个对象卡输出什么字段？字段名是否统一？
- 对象 A 的信号如何影响对象 B 的过滤决策？
- 日线选股和分钟级执行谁在先谁在后？
- 一个交易信号需要几张对象卡"投票同意"才能触发？
- 从"已冻结"升级到"proxy_quantizable_now"需要什么证据？

这份文档回答上述问题，但不写任何可执行代码。

### 1.2 核心设计原则

| 原则 | 说明 |
|------|------|
| **只读结构，不预测** | 对象卡只描述市场结构，不预测未来价格 |
| **保守升级** | 只有回测证据充分时才允许成熟度升级 |
| **互锁优先** | 任何信号必须先通过互锁检查，才能进入投票池 |
| **T+1 约束** | A 股所有设计默认考虑 T+1 惩罚，除非明确标注为日内策略 |

## 2. 回测引擎输入规范

### 2.1 统一输出接口（所有对象卡必须遵守）

每个对象卡无论内部逻辑多复杂，对外输出必须封装为以下**标准字段包**。回测引擎只消费这些标准字段，不直接读取对象卡内部中间变量。

#### 2.1.1 基础信息字段（必填）

```text
object_id           STRING      -- 对象卡唯一标识，如 "CHZL_BSD_P0_E"
object_name         STRING      -- 人类可读名称，如 "缠论三类买卖点"
function_bucket     ENUM        -- 功能层：STRUCTURE / ENERGY / EXECUTION / RISK / SELECTION / PORTFOLIO
process_layer       ENUM        -- 处理层：FEATURE / SIGNAL / FILTER / POSITION / EXECUTION_CONSTRAINT
timestamp           TIMESTAMP   -- 信号生成时间戳（精确到 K 线级别）
symbol              STRING      -- 标的代码，如 "000001.SZ"
timeframe           ENUM        -- 时间框架：DAILY / WEEKLY / 60MIN / 15MIN / 5MIN / 1MIN
```

#### 2.1.2 信号核心字段（至少填一项）

```text
signal_type         ENUM        -- 信号类型：
                                --   'NONE' = 无信号
                                --   'LONG' = 做多信号
                                --   'SHORT' = 做空信号（A 股纯多头下不可用）
                                --   'FILTER_PASS' = 过滤器通过（无方向）
                                --   'FILTER_BLOCK' = 过滤器阻断（无方向）
                                --   'ENHANCE' = 增强其他信号（无独立方向）
                                --   'DOWGRADE' = 降级其他信号（无独立方向）
                                --   'CONTEXT' = 仅背景信息，不干预交易

signal_strength     INT(0-10)   -- 信号强度：0=无信号，5=中等，10=极强
                                -- 执行层对象通常 ≥ 5 才有投票权
                                -- 选股层/风控层对象通常 ≥ 3 即可参与过滤

signal_confidence   FLOAT(0-1)  -- 信号置信度（对象卡内部评估）
                                -- < 0.3 的信号视为噪音，不进入投票池
                                -- 缠论背驰的 confidence 规则已冻结：0.3 过滤线
```

#### 2.1.3 互锁字段（执行层必填，其他层可选）

```text
lock_status         ENUM        -- 互锁状态：
                                --   'LOCKED' = 该对象卡已锁定，信号稳定
                                --   'UNLOCKED' = 该对象卡未锁定，信号可能变化
                                --   'CONFLICT' = 与该对象卡互锁的其他对象卡存在冲突
                                --   'EXPIRED' = 信号已过期（如 YTC 的 15 根 K 线超时）

lock_reason         STRING      -- 锁定原因简述，如 "多周期对齐确认" "KD 周线极端区共振"
                                -- 解锁原因：如 "15min 周期反转，锁定解除"
```

#### 2.1.4 过滤操作字段（过滤器/风控层必填）

```text
filter_action       ENUM        -- 对上游信号的操作：
                                --   'PASS' = 通过，不影响
                                --   'ENHANCE' = 增强（如 MFLOW 主力流入增强 KD 买入）
                                --   'DOWNGRADE' = 降级（如 MFLOW 主力流出降低 KD 信号强度）
                                --   'BLOCK' = 阻断（如 VolTarget 极端波动强制降仓）
                                --   'CONTEXT_ONLY' = 仅作为背景信息，不干预（如 INSTB）
                                --   'REVERSE' = 反向（极端情况下，如 ATRATIO 纯多头无效）

target_object_id    STRING      -- filter_action 的作用对象，如 "KD_MTF_P0"
                                -- 为空表示对所有上游信号生效
```

#### 2.1.5 风控字段（风控层必填，其他层可选）

```text
risk_action         ENUM        -- 风控操作：
                                --   'NONE' = 无风控操作
                                --   'REDUCE_SIZE' = 降低仓位（如 Kelly 半凯利）
                                --   'INCREASE_SIZE' = 增加仓位（如低波动环境）
                                --   'FORCE_CLOSE' = 强制平仓（如 Van Tharp 2% 硬性上限触发）
                                --   'HALT_NEW' = 暂停新入场（如 VolTarget 极端波动）
                                --   'CRISIS_MODE' = 危机模式（Kelly 连续亏损 3 笔）

size_scalar         FLOAT       -- 仓位缩放系数：
                                --   1.0 = 标准仓位
                                --   < 1.0 = 降仓（如 Kelly 半凯利 → 0.5）
                                --   > 1.0 = 加仓（如低波动环境允许，但 A 股单票上限 20%）
                                --   0.0 = 禁止任何仓位（强制空仓）

stop_adjustment     FLOAT       -- 止损调整（ATR 倍数偏移）：
                                --   0.0 = 不调整
                                --   正值 = 止损放宽（如 A 股小盘股）
                                --   负值 = 止损收紧（如高波动环境）
```

#### 2.1.6 元数据字段（必填）

```text
maturity_status     ENUM        -- 该对象卡当前成熟度：
                                --   'FROZEN_FIELDS' = 已冻结核心字段（本文档阶段）
                                --   'PSEUDO_TESTED' = 伪代码验证通过
                                --   'SINGLE_FACTOR_BT' = 单因子回测通过
                                --   'COMBINED_BT' = 组合回测通过
                                --   'OUT_OF_SAMPLE' = 样本外测试通过
                                --   'PROXY_QUANTIZABLE' = 可正式接入回测引擎

data_requirement    ENUM        -- 数据需求：
                                --   'OHLCV' = 只需日频 K 线
                                --   'OHLCV_INTRADAY' = 需要分钟级 K 线
                                --   'LEVEL2' = 需要 Level-2 逐笔数据
                                --   'QUARTERLY' = 需要季度财务数据
                                --   'FUND_FLOW' = 需要资金流向数据
                                --   'MULTI' = 需要多种数据源

effectiveness_scope ENUM        -- 有效范围：
                                --   'ASHARE_LONG_ONLY' = A 股纯多头
                                --   'ASHARE_LONG_SHORT' = A 股多空（需股指期货）
                                --   'GLOBAL' = 跨市场通用（外汇/期货/币圈）
                                --   'ASHARE_METHOD' = A 股方法层参考（不干预执行）
```

### 2.2 接口验证规则（回测引擎的硬性检查）

回测引擎在消费任何对象卡输出前，必须执行以下检查。任一检查失败，该对象卡输出被丢弃，不参与后续计算。

```text
验证规则 1：timestamp 必须在该 K 线收盘后（避免未来信息泄露）
验证规则 2：signal_confidence < 0.3 的 signal_type 强制设为 'NONE'
验证规则 3：filter_action = 'BLOCK' 时，必须有 target_object_id 或明确标注为 "GLOBAL_BLOCK"
验证规则 4：risk_action = 'FORCE_CLOSE' 时，必须附带 stop_adjustment 和 size_scalar 字段
验证规则 5：timeframe 必须与该对象卡声明的 process_layer 兼容（如 SELECTION 层不支持 1MIN）
验证规则 6：ASHARE_LONG_ONLY 环境下，任何 signal_type = 'SHORT' 的输出被丢弃
验证规则 7：data_requirement 必须与当前数据环境匹配（无 Level-2 时丢弃 LEVEL2 依赖对象卡）
```

### 3.2 执行顺序规则（硬性约束）

```text
规则 1：高时间框架优先
  - 周线信号必须先于日线信号计算
  - 如果周线 KD_MTF 发出 'CONFLICT' 或 'UNLOCKED'，日线 Pipeline 不执行选股
  - 周线上下文注入日线时，只传递 signal_type 和 lock_status，不传递具体字段

规则 2：选股层必须先于执行层
  - 日线 SELECTION 层（MFLOW/VOLFAC/INSTB/ATRATIO）必须在 STRUCTURE 层之前计算
  - 被 SELECTION 层 BLOCK 的标的，不进入 STRUCTURE 层计算（节省算力）
  - SELECTION 层输出 filter_action 为 'BLOCK' 时，该标的当日 Pipeline 终止

规则 3：风控层必须在投票前最后介入
  - 所有 SIGNAL 和 FILTER 的输出先进入 VOTE_POOL
  - 风控层（KELLY/VOLTARGET/THARP）在投票前对 VOTE_POOL 中的信号进行调制
  - 调制方式：risk_action 和 size_scalar 调整，不直接删除信号（保留审计追踪）

规则 4：投票通过后，风控层再次介入
  - VOTE_POOL 投票通过后（≥3），信号进入 EXEC 阶段
  - 风控层再次检查：Van Tharp 2% 硬性上限是否被突破？VolTarget 是否强制 HALT_NEW？
  - 若触发硬性风控，信号被强制降级为 'ABORT'
```

### 3.3 跨时间框架上下文注入规范

```text
注入方向：周线 → 日线 → 分钟级（单向，不反向）
注入内容：
  - signal_type（信号类型）
  - signal_strength（信号强度，作为下限基准）
  - lock_status（互锁状态）
  - lock_reason（锁定原因）

不注入内容（避免信息泄露）：
  - 具体的 stop_adjustment 数值（不同时间框架止损逻辑不同）
  - size_scalar（各时间框架独立风控）
  - 对象卡内部中间字段

接收规则（低时间框架如何处理注入的上下文）：
  - 如果周线 signal_type = 'LONG' 且 lock_status = 'LOCKED'：
    → 日线 SIGNAL 层的 signal_strength 最低为 5（不能低于周线确认的强度）
  - 如果周线 lock_status = 'CONFLICT'：
    → 日线 Pipeline 中所有对象的 signal_confidence 强制 × 0.5（降级）
  - 如果周线 signal_type = 'NONE'：
    → 不影响日线，日线独立计算（多周期共振是增强，不是前提）
```

## 4. 投票与信号融合规则

### 4.1 投票池（VOTE_POOL）的构成

每个时间框架的 Pipeline 末端，所有 SIGNAL 层和 FILTER 层的对象卡输出进入 VOTE_POOL。但**不是所有对象卡都有投票权**。

#### 4.1.1 有投票权的对象（必须满足全部条件）

```text
条件 1：function_bucket = 'EXECUTION' 或 'FILTER'
条件 2：signal_type ∈ {'LONG', 'SHORT', 'FILTER_PASS'}
条件 3：signal_strength ≥ 5
条件 4：lock_status ∈ {'LOCKED', 'UNLOCKED'}（'CONFLICT' 和 'EXPIRED' 无投票权）
条件 5：signal_confidence ≥ 0.3
条件 6：maturity_status ∈ {'SINGLE_FACTOR_BT', 'COMBINED_BT', 'OUT_OF_SAMPLE', 'PROXY_QUANTIZABLE'}
```

#### 4.1.2 当前有投票权的对象卡清单（基于 12 张已冻结卡）

```text
日线级别：
  ✓ CHZL_BSD_P0_E（signal_strength ≥ 5 时，1Buy/2Buy/3Buy 均有投票权）
  ✓ BPB_P0_E（突破质量 ≥ 0.3 时）
  ✓ TKR7_P0_E（AO 背离确认时，常规背离 strength 5，隐藏背离 strength 6）
  ✓ YTC_P0_E（TST/BOF/BPB 确认后，但需 ytc_srf_is_valid=True）
  ✓ VP_P0_E（VA 突破信号，但 volume_integrity_score ≥ 0.6）
  ✗ KD_MTF_P0（STRUCTURE 层，无独立投票权，但作为互锁上下文注入）
  ✗ CHZL_BEICHI（FILTER 层，无独立投票权，仅作为过滤条件）

分钟级别（TK 外汇体系）：
  ✓ TK_R6_P0_E（5 级状态机中 TOUCH_BOUNCE 及以上）
  ✓ TK_R7_P0_E（AO 背离确认，与日线 TKR7 功能相似但时间框架不同）
  ✓ TK_R8_P0_E（ABC 资格判定通过后）
  ✓ BPB_P0_E（日线和分钟级均可，但需分别计算）
  ✓ VP_P0_E（分钟级 VA 突破，需 5min 数据）

风控层：
  ✗ KELLY_P0_R（无投票权，仅在投票前和投票后调制 size_scalar）
  ✗ VOLTARGET_P0_R（无投票权，仅调制 size_scalar 和 stop_adjustment）
  ✗ THARP_RISK（无投票权，仅触发 FORCE_CLOSE 和 HALT_NEW）

选股层：
  ✗ MFLOW_P0_A（无投票权，仅作为 FILTER，filter_action 影响投票池）
  ✗ VOLFAC_P0_A（无投票权，仅作为 FILTER）
  ✗ ATRATIO_P0_A（ASHARE_LONG_ONLY 下无投票权，LIMITED_CANDIDATE）
  ✗ INSTB_P0_A（无投票权，CONTEXT_ONLY）
```

### 4.2 投票规则（entry_min_votes = 3）

```text
规则 1：最小投票数
  - 日线级别：至少 3 个有投票权的对象投 'LONG'（或 'FILTER_PASS'）票，才能触发执行
  - 分钟级别：至少 3 个有投票权的对象投 'LONG'（或 'SHORT'，若允许）票，才能触发执行
  - 投票数 < 3 → 信号降级为 'ABORT'，不进入 EXEC 阶段

规则 2：多周期共振加分
  - 如果有 2 个时间框架同时出现 ≥ 3 票（如日线和周线），总投票数按加权计算：
    → 周线票 × 1.5 权重 + 日线票 × 1.0 权重 + 分钟票 × 0.8 权重
  - 加权总分 ≥ 5 时，signal_strength 额外 +1（从 5→6 或 6→7）

规则 3：过滤器否决权
  - 任何 FILTER 层对象输出 filter_action = 'BLOCK' 且 target_object_id 包含该信号源时：
    → 该信号源的投票被扣除（相当于从 "赞成" 变为 "弃权"）
  - 如果 MFLOW 输出 'BLOCK'（主力出逃）且 target = 'CHZL_BSD'：
    → CHZL_BSD 的投票被扣除，需其他对象补足投票数

规则 4：风控层一票否决（硬性）
  - Van Tharp 2% 硬性上限触发 → 无论多少票，强制 'ABORT'
  - VolTarget 输出 HALT_NEW → 暂停新入场，已有持仓按正常止损处理
  - Kelly 危机模式（连续亏损 3 笔）→ 所有新信号 strength -2，可能导致投票不足

规则 5：投票对象来源限制
  - 同一功能 bucket 的对象最多贡献 2 票（防止单一维度过度集中）
  - 例如：EXECUTION 层最多贡献 2 票，超过 2 票的 EXECUTION 对象只取 strength 最高的 2 个
  - 但 FILTER 层的 'FILTER_PASS' 不计入此限制（因为 FILTER 层是必要条件而非充分条件）
```

### 4.3 投票融合后的最终信号生成

```text
步骤 1：收集所有有投票权对象的 signal_type
步骤 2：计算赞成票、反对票、弃权票
步骤 3：应用过滤器否决（扣除被 BLOCK 的票）
步骤 4：应用风控层一票否决（如触发）
步骤 5：检查加权总分是否 ≥ 3
步骤 6：若通过，计算最终信号：
         final_signal_type = 'LONG'（如果赞成票 > 反对票）
         final_signal_strength = min(10, 平均赞成票 strength + 多周期共振加分)
         final_size_scalar = min(所有风控层 size_scalar)  # 取最保守的
         final_stop_adjustment = 所有风控层 stop_adjustment 的加权平均
步骤 7：若未通过，final_signal_type = 'ABORT'，并记录原因（票数不足/风控否决/过滤器阻断）
```

### 5.1 升级路径定义

### 5.2 每个阶段的验收标准（零代码阶段只需 v1.0→v1.1）

#### 阶段 1：伪代码验证（v1.0 → v1.1）

```text
验收条件 1：字段完备性检查
  - 对象卡输出字段是否覆盖标准接口的全部必填项？
  - 字段名是否符合命名规范（小写下划线，无缩写歧义）？
  - 字段类型定义是否明确（ENUM 值是否穷举、FLOAT 范围是否标注）？

验收条件 2：互锁逻辑闭环检查
  - 该对象卡至少与 3 个其他对象卡存在互锁关系？
  - 互锁规则是否有明确的触发条件和结果？
  - 是否存在循环互锁（A 依赖 B，B 依赖 C，C 依赖 A）？

验收条件 3：失效模式覆盖检查
  - 是否列出至少 3 种失效场景？
  - 每种失效场景是否有明确的降级处理（如标记为 'market_halt'、'insufficient_data'）？
  - 失效场景是否覆盖了数据缺失、极端行情、模型假设破坏三种类型？

验收条件 4：A 股适配检查（若为 A 股对象）
  - 是否考虑了 T+1 约束？
  - 是否考虑了涨跌停？
  - 是否考虑了小盘股特殊性？
  - 是否标注了需要 Level-2 或另类数据的字段？

验收条件 5：伪代码可执行性检查
  - 伪代码是否存在逻辑死循环？
  - 伪代码中所有输入参数是否已定义？
  - 伪代码输出是否与字段定义一致？
  - 伪代码是否标注了关键阈值（如 0.3、0.5、0.618）的来源或假设？

通过标准：5 项全部满足 → 升级至 v1.1（伪代码验证通过）
```

#### 阶段 2：单因子回测（v1.1 → v1.2）

```text
验收条件 1：回测参数文档化
  - 回测区间：至少覆盖 2018-2024（包含 2018 熊市、2020 疫情、2021 结构牛、2024 震荡）
  - 股票池：全 A 股或至少 800 只成分股（排除 ST、新股、退市股）
  - 交易成本：双边 0.25%（印花税 + 佣金 + 滑点）
  - 再平衡频率：与该对象卡的 timeframe 一致（日线对象日频，周线对象周频）

验收条件 2：核心指标阈值
  - 年化收益率 > 0（正收益）
  - 最大回撤 < 30%
  - 夏普比率 > 0.5（最低可接受门槛）
  - 胜率 > 40%（对于趋势策略）或 > 35%（对于反转策略）
  - 盈亏比 > 1.2

验收条件 3：参数敏感度分析
  - 核心参数（如 ATR 倍数、回撤深度阈值）在 ±20% 范围内变化时：
    → 年化收益率变化不超过 ±30%
    → 最大回撤变化不超过 ±20%
  - 若敏感度太高，说明参数过拟合，需重新设计

验收条件 4：失效场景验证
  - 在回测中故意触发失效模式（如删除 30% 资金流向数据）：
    → 对象卡应降级处理，不输出假信号
    → 降级后的表现不应劣于 "无信号"（即不交易）

通过标准：4 项全部满足 → 升级至 v1.2（单因子回测通过）
```

#### 阶段 3：组合回测（v1.2 → v1.3）

```text
验收条件 1：互锁验证
  - 该对象卡与其他对象卡同时运行时，互锁规则是否按预期触发？
  - 互锁是否导致信号过度过滤（如 90% 的信号被过滤掉）？
  - 互锁是否导致信号冲突无法解决（如两个对象卡同时发出 BLOCK 和 ENHANCE）？

验收条件 2：投票机制验证
  - 该对象卡在 VOTE_POOL 中的表现：
    → 投票通过率（被采纳的信号 / 发出的信号）应在 30%-70% 之间
    → 通过率 < 30% → 信号过于激进，需提高阈值
    → 通过率 > 70% → 信号过于保守，可能错过机会

验收条件 3：组合绩效提升
  - 加入该对象卡后，组合的年化夏普是否提升？
  - 加入该对象卡后，组合的最大回撤是否降低？
  - 若加入后组合绩效反而下降，需重新评估该对象卡的定位

通过标准：3 项全部满足 → 升级至 v1.3（组合回测通过）
```

#### 阶段 4：样本外测试（v1.3 → v1.4 / proxy_quantizable_now）

```text
验收条件 1：样本外区间
  - 样本外区间至少 6 个月，且与样本内区间不重叠
  - 样本外区间应包含至少一次市场风格切换（如价值→成长、大盘股→小盘股）

验收条件 2：绩效衰减控制
  - 样本外夏普比率不应低于样本内夏普的 70%
  - 样本外最大回撤不应超过样本内最大回撤的 120%
  - 若衰减过大，说明过拟合，需退回 v1.2 重新优化

验收条件 3：极端行情表现
  - 样本外区间应包含至少一次极端行情（如连续跌停、黑天鹅事件）
  - 对象卡在极端行情下的表现应优于 "无信号"（即不交易）
  - 对象卡不应在极端行情中发出大量假信号

通过标准：3 项全部满足 → 升级至 proxy_quantizable_now（可正式接入回测引擎）
```

## 6. 回测引擎的"无信号"基准

### 6.1 为什么需要"无信号"基准

回测框架的验收标准中，多次出现 "不应劣于无信号"。这里的"无信号"不是指不运行回测，而是指**所有对象卡输出 signal_type = 'NONE' 时的基准表现**。

```text
"无信号"基准的三种定义：

定义 A：纯现金持有
  - 策略：始终持有现金，不交易
  - 收益：0%（无风险利率忽略）
  - 用途：验证对象卡是否 "正期望"（即是否比不交易好）

定义 B：买入持有基准
  - 策略：在回测起点等权买入所有标的，持有到期
  - 收益：市场平均收益
  - 用途：验证对象卡是否 "有超额收益"（即是否跑赢市场）

定义 C：随机交易基准
  - 策略：随机选择标的和方向，频率与对象卡相同
  - 收益：接近 0（扣除交易成本后通常为负）
  - 用途：验证对象卡是否 "有信息优势"（即是否比随机好）

验收标准中的 "无信号" 默认采用定义 A（纯现金持有），但鼓励同时提供定义 B（买入持有）作为参考。
```

### 6.2 "无信号"基准的应用场景

```text
场景 1：对象卡失效时
  - 当数据缺失或极端行情触发失效模式时，对象卡应输出 'NONE'
  - 如果此时对象卡输出假信号（如随机猜测），其表现应劣于 "无信号"
  - 验收：失效模式下的表现 ≥ 纯现金持有

场景 2：参数敏感度分析
  - 当参数偏移导致对象卡表现下降时，下降幅度不应使对象卡劣于 "无信号"
  - 验收：参数 ±20% 偏移后的表现 ≥ 纯现金持有

场景 3：组合回测中
  - 如果某对象卡加入组合后组合表现反而下降，说明该对象卡与组合其他成员冲突
  - 验收：加入该对象卡后的组合夏普 ≥ 不加入该对象卡的组合夏普
```
