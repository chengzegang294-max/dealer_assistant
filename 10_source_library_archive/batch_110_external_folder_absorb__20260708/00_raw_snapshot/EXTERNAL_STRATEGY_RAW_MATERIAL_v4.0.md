## 一、订单路由与执行系统（OMS/EMS）

### 1.1 标准高性能交易链路

来源：[TechNova - 高频交易系统中的"无效"风暴](https://technologynova.org/)

```
[客户端] → [接入网关 (Gateway)] → [风控前置 (Pre-Risk)] → [序号生成器 (Sequencer)] → [撮合引擎 (Matching Engine)] → [行情发布 (Market Data)] & [清结算 (Clearing)]
```

**关键模块**：
- **接入网关**：协议转换（FIX 等）、路由器、在途订单管理器（In-Flight Order Manager）
- **风控前置**：独立于主交易路径，独立协程池执行，避免阻塞主路径（延迟目标 <500ns）
- **报盘服务**：订单结构转换、报送交易所、收取确认/成交/废单、推送回订阅方
- **排队服务**：接受订单并排队、生成唯一标识；设计为冗余式多活
- **仲裁服务**：维护主从状态、灾难后主从切换

### 1.2 领域服务分层（DDD 在高频交易中的落地）

来源：[CSDN - 全球 C++ 专家齐聚解密 DDD](https://blog.csdn.net/CompiTide/article/details/155164464)

典型四层结构：

| 层级 | 职责 | 延迟目标 | 性能隔离 |
|------|------|----------|----------|
| 接入层 | 协议编解码、连接管理 | <1μs | CPU 绑核 Core 0-1 |
| 网关层 | 消息路由、流量整形 | <1μs | CPU 绑核 Core 0-1 |
| 领域层 | 核心交易逻辑、状态机控制 | <500ns | CPU 绑核 Core 2-3 |
| 持久层 | 异步日志写入、快照存储 | 异步 | 独立 IO 线程 |

**关键设计模式**：
```
func SubmitOrder(order) error:
    if !riskSvc.Validate(order) {  // 风控前置 → 独立协程池
        return ErrRiskRejected
    }
    return orderDomain.Submit(order)  // 提交至领域服务
```

> **Kimi 取舍**：四层结构对个人量化而言过于重。保留"风控前置独立执行"和"订单状态机"思想，映射为 Python 中的异步风控检查 + 订单生命周期管理。

## 二、A 股券商对接与柜台系统

### 2.1 券商柜台架构

来源：[叩富网 - 一文了解券商的交易柜台系统](https://licai.cofool.com/user/guide_view_2576340.html)

**核心约束**：
> 依据国内监管要求，客户无法直连交易所系统，中间必须经过经纪公司的柜台系统，由经纪公司柜台系统调用交易所 API 下单。

**主流券商系统（金证 / 恒生 / 金仕达）三层结构**：

```
┌─────────────────────────────────────────────────────┐
│                   报盘系统                            │  ← 个人用户不可用
├─────────────────────────────────────────────────────┤
│                   接口数据库                          │  ← 第三方软件用（通达信/同花顺）
├─────────────────────────────────────────────────────┤
│                   柜台系统                            │  ← 个人程序化投资者用
│  ├─ 账户业务（开户/销户/权限管理）                     │
│  ├─ 资金业务（三方存管）                               │
│  ├─ 证券交易业务（委托/成交指令对接）                   │
│  ├─ 信用交易业务（融资融券）                           │
│  ├─ 基金代销业务                                     │
│  └─ 清算业务（资金/股份清算结算）                      │
└─────────────────────────────────────────────────────┘
```

**接口类型**：
- **券商私有接口 API**：供第三方金融软件公司（通达信、同花顺）
- **券商接口 API**：封装后供个人程序化投资者（即我们使用的接口）
- **报盘接口 API**：仅券商系统提供商及其合作伙伴可用，个人不可用

### 2.2 交易通道层级

来源：[搜狐 - 快速通道、极速柜台、独立交易单元区别](https://www.sohu.com/)

| 类型 | 定位 | 适用场景 | 成本 |
|------|------|----------|------|
| **VIP 快速通道** | "高速公路"，缩短中间路径损耗 | 盘中追快速上涨票，减少滑点 | 低（通常免费） |
| **极速柜台** | "高铁"，部署在交易所机房 | 量化/套利交易，QMT/Ptrade 支持 | 中（需申请） |
| **独立交易单元** | 通道独享，无排队 | 集合竞价优势、追开板涨停 | 高（年费数万） |

**程序化交易接入优化方式**（来源：[知乎 - 低延迟柜台演变](https://zhuanlan.zhihu.com/p/529495647)）：
- 部署方式：托管到交易所机房 / 双中心（沪深各一）
- 行情接入：申请单独 Level-2 通道
- 独立席位：申请独立交易所席位
- 升级 API：UDP 报单、低时延网卡

> **Kimi 取舍**：用户为 Windows 单机部署，跳过 FPGA/托管机房/独立席位。重点关注 **QMT/Ptrade 的 Python API 接口**、**普通柜台接口**、**Level-2 行情**这三个落地层面。

### 2.3 Ptrade API 关键接口（恒生出品）

来源：[Ptrade API 文档](https://ptradeapi.com/)

**关键交易函数**：

```python
# 指定目标数量买卖（回测+交易模块通用）
order_target(security, amount, limit_price=None)
# ⚠️ 注意：持仓同步有6秒时滞，可能造成重复下单
# 建议：增加订单和持仓同步管理

# 指定持仓市值买卖
order_target_value(security, value, limit_price=None)
# ⚠️ 同上，注意重复下单风险

# 滑点设置（回测模块专用）
set_fixed_slippage(fixedslippage=0.0)   # 固定滑点（元）
set_slippage(slippage=0.1)              # 滑点比例（%，默认0.1%）
```

**关键约束**：
- 股票委托取整 100 股，可转债取整 10 张
- 交易场景 limit_price 不填时默认用行情快照最新价
- 持仓数据同步有 6 秒时滞（柜台配置决定）
- 柜台返回持仓是否体现当日变化由券商配置决定
- 需配合在途订单管理（cancel → re-order 需处理前一笔未完全成交）

## 三、风控前置（Pre-Trade Risk）

### 3.1 实时风控守护进程设计

来源：[Quant67 - 运维与合规：监控、熔断、监管报送、复盘](https://quant67.com/tags/circuit-breaker.html)

**核心思想**：
> 量化交易系统的运维不像普通互联网服务：故障窗口以毫秒计，每一次错误直接对应金钱损失。

**实时风控守护进程功能**：
1. **订单速率限制**：防止策略异常导致订单风暴（如因子计算错误产生大量重复信号）
2. **PnL Drawdown 监控**：实时计算账户 PnL，达到回撤阈值触发熔断
3. **熔断触发**：自动暂停交易、关闭策略信号、发送告警
4. **SLO 与 Error Budget**：量化计算可接受的错误率，例如日交易错误率 <0.1%

**风控检查清单（Pre-Trade）**：
- 单笔金额限制
- 单日累计金额限制
- 持仓集中度限制
- 标的白名单/黑名单
- 交易时间窗口检查（避免非交易时段下单）
- 涨跌停保护（涨停不卖、跌停不买）
- 停牌/退市检查
- 账户可用资金/可用持仓检查

### 3.2 风控独立执行原则

来源：CSDN DDD 文章

```
风控校验在独立协程/线程池中执行，避免阻塞主交易路径。
关键路径延迟目标：行情解码 <1μs，订单处理 <500ns。
```

> **Kimi 映射**：在 Python 中，风控检查应在 `asyncio` 独立任务中执行，或通过线程池隔离。主交易逻辑（信号→下单）不应等待风控检查完成，而是在下单前调用风控 gate（轻量检查）。

## 四、滑点与延迟管理

### 4.1 回测中的实盘修正

来源：[腾讯云/火山引擎 - 金融数据 API 接入](https://developer.cloud.tencent.com/)

**三种修正方法缩小回测与实盘差距**：

| 修正方法 | 实现方式 | 适用场景 |
|----------|----------|----------|
| **滑点建模** | 添加随机滑点 0.05%~0.2% | 回测阶段 |
| **流动性影响处理** | 大额订单（>1分钟平均成交额10%）用 VWAP 拆分 | 执行阶段 |
| **延迟补偿** | 回测中增加 50~100ms 固定延迟 | 回测阶段 |

**滑点调整规则**：
- 蓝筹股：0.05%~0.1%
- 小盘股：0.1%~0.2%
- 极端流动性缺失时：0.2%+

### 4.2 执行模拟器分级

来源：[WaylandZ - 第19课：执行系统](https://waylandz.com/quant-book/)

**执行系统关键概念**：
```
真实成交数据 = 成交价 + 滑点 + 概率/延迟 + 交易规则/摩擦成本
```

**用 K 线 Close 当成交价会系统性高估策略可实现性。**

**演进路径**：
```
保守模拟器（固定滑点+延迟） → 小资金实盘采样 → 反向校准模拟器
```

**实盘数据闭环**：必须记录以下字段才能校准执行模型：
- A 类数据（市场环境）：只能近似（行情快照/Level-2）
- B 类数据（实盘日志）：订单发送时间、委托价格、成交价格、成交时间、订单状态、取消原因

### 4.3 在途订单管理（In-Flight Order Manager）

来源：[TechNova](https://technologynova.org/)

**传统网关无状态 → 改造为"轻状态"**：

```
在途订单管理器（In-Flight Order Manager）
  ├─ 跟踪所有已发送但未最终确认的订单
  ├─ 维护订单状态机：PENDING → SUBMITTED → PARTIAL_FILLED → FILLED / CANCELLED / REJECTED
  ├─ 撤单优化：识别已离开网关的订单，避免无效撤单请求
  └─ 防重复：订单唯一标识（UUID + 序号）
```

> **Kimi 映射**：在 Python 中维护 `dict[order_id, OrderState]`，定期与券商查询接口同步。订单状态机必须精确：发单 → 待确认 → 已确认 → 部分成交/全部成交/已撤单/废单。

## 五、交易监控与实时 P&L

### 5.1 监控分层体系

来源：[Quant67 - 运维与合规](https://quant67.com/)

**监控层级**：

```
Layer 1: 基础设施监控（CPU/内存/磁盘/网络）
Layer 2: 应用监控（进程存活/日志异常/接口响应时间）
Layer 3: 交易监控（订单成功率/成交率/撤单率/废单率）
Layer 4: 业务监控（PnL/回撤/持仓/策略绩效）
Layer 5: 合规监控（交易频率/异常交易行为/监管报送）
```

**关键指标**：

| 指标 | 类型 | 预警阈值 | 熔断阈值 |
|------|------|----------|----------|
| 日 PnL 回撤 | 资金 | > 3% | > 5% |
| 单笔亏损 | 资金 | > 1% | > 2% |
| 订单失败率 | 执行 | > 1% | > 5% |
| 废单率 | 执行 | > 0.5% | > 2% |
| 策略信号延迟 | 技术 | > 500ms | > 2s |
| 行情延迟 | 技术 | > 1s | > 5s |

### 5.2 实时 P&L 计算

来源：[知乎 - 极速交易系统设计与实践](https://zhuanlan.zhihu.com/p/613367713)

**T日实时核算**：
- 现货按移动平均成本法记录每笔交易成本（成交金额 + 费用）
- 收盘后根据交易记录自动生成资金流水，核算资金、持仓
- 实时 P&L = ∑(当前持仓 × 最新价 - 持仓成本) + ∑(已成交盈亏) - 交易费用

## 六、灾难恢复与高可用

### 6.1 灾难恢复技术框架

来源：[叩富网 - 灾难恢复技术优化量化交易系统](https://licai.cofool.com/ask/qa_4552640_1_2.html)

**7 大措施**：

1. **灾难恢复计划**：定义 RTO（恢复时间目标）和 RPO（恢复点目标）
2. **数据备份与恢复**：实时数据备份、异地备份、数据完整性验证
3. **冗余设计**：硬件冗余、网络冗余、软件冗余（容器化）
4. **系统架构优化**：分布式架构、微服务、负载均衡
5. **容错与故障切换**：自动故障切换、回滚机制
6. **定期灾难恢复演练**：模拟真实场景、评估改进
7. **监控与预警**：实时监控、预警阈值

**RTO/RPO 建议值**（个人量化场景）：
- RTO（恢复时间）：< 5 分钟（自动重启策略进程）
- RPO（恢复点）：< 1 分钟（交易日志实时写入磁盘）

### 6.2 量化交易易被忽略的细节

来源：[CSDN - 量化交易容易被忽略的细节](https://blog.csdn.net/august_81/article/details/145713470)

**数据层面**：
- 数据清洗不彻底（缺失值、异常值、重复记录）
- 数据频率与粒度不匹配（高频策略用低频数据）
- 忽略分红、拆股等公司行为（需用复权数据）

**风险管理层面**：
- 忽视尾部风险（黑天鹅）→ 引入压力测试、动态止损
- 头寸管理不当 → 设定最大持仓比例、使用凯利公式
- 缺乏实时监控 → 跟踪 PnL/回撤、预警机制

**心理层面**：
- 过度干预（频繁调整参数）→ 制定规则、严格执行
- 忽视心理偏差 → 自动化减少人为干预

| 剔除内容 | 原因 |

### 7.3 新增设计方向（基于搜索启发）

1. **回测诚实性参数包**：滑点 0.05%~0.2% + 延迟 50~100ms + 流动性影响 VWAP 阈值
2. **订单生命周期管理模块**：状态机 + 在途订单管理 + 券商同步（6秒时滞补偿）
3. **运行时风控守护进程**：订单速率限制 + PnL drawdown 熔断 + 信号延迟监控
4. **券商接口抽象层**：统一 QMT/Ptrade/其他柜台的 Python API
5. **实时账户与 P&L 模块**：移动平均成本法 + 实时持仓 + 资金流水
6. **监控与告警模块**：五层监控 + 关键指标阈值 + 通知机制（日志/弹窗/邮件）
7. **灾难恢复机制**：进程守护 + 交易日志实时持久化 + 自动重启
