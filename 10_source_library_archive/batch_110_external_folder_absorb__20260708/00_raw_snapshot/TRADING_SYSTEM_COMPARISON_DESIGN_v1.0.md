## 三、值得借鉴的具体设计

### 3.1 从 vn.py 借鉴：模块化架构

vn.py 的模块划分最值得参考：

```
vn.py 架构：
├── vnpy.event       ← 事件引擎（核心，所有模块通信通过事件）
├── vnpy.trader      ← 交易核心（账户、持仓、订单、合约）
├── vnpy.gateway     ← 交易接口（CTP、IB、XTP...统一抽象）
├── vnpy.app         ← 应用模块（CTA、套利、算法交易...）
├── vnpy.chart       ← K 线图表
└── vnpy.risk        ← 风控模块

我们的映射：
├── src/data_pipeline       ← 数据管道（对应 vnpy.data）
├── src/backtest_engine     ← 回测引擎（对应 vnpy.app 中的回测）
│   ├── pipeline.py         ← 事件驱动 Pipeline（对应 vnpy.event）
│   ├── objects/            ← 对象卡（对应 vnpy.app 中的策略）
│   ├── vote/               ← 投票引擎（vn.py 无直接对应，自创）
│   ├── risk/               ← 风控层（对应 vnpy.risk）
│   └── execution/          ← 执行层（对应 vnpy.trader）
├── src/trading_engine      ← 实盘引擎（对应 vnpy.trader + gateway）
│   ├── broker/             ← 券商接口抽象（对应 vnpy.gateway）
│   ├── execution/          ← 订单管理（对应 vnpy.trader）
│   ├── account/            ← 账户与监控（扩展）
│   └── persistence/        ← 持久化（扩展）
└── src/governance          ← 治理架构（vn.py 无对应，自创）
```

**关键借鉴点**：
1. **统一事件引擎**：所有模块通过事件通信，解耦
2. **Gateway 抽象**：券商接口统一抽象，切换券商只需换 Gateway
3. **App 插件化**：策略/应用模块可插拔

### 3.2 从 Backtrader 借鉴：Cerebro 引擎设计

Backtrader 的 Cerebro 引擎设计清晰：

```python
# Backtrader 风格
cerebro = bt.Cerebro()                    # 创建引擎
cerebro.addstrategy(MyStrategy)           # 添加策略
cerebro.adddata(data)                     # 添加数据
cerebro.addanalyzer(bt.analyzers.SharpeRatio)  # 添加分析器
cerebro.run()                             # 运行
cerebro.plot()                            # 绘图

# 我们的映射（更复杂，因为有多层决策）
engine = TradingEngine(mode=TradingMode.BACKTEST)
engine.load_data(symbols=["000001.SZ"], start="2020-01-01", end="2020-12-31")
engine.register_objects([VOLFAC(), TKR7(), BPB(), VP()])  # 对象卡
engine.set_strategy_bundle(TrendFollowing)                # 策略组合
engine.set_risk_config(RiskConfig())                      # 风控
engine.run()                                              # 运行
engine.generate_report()                                  # 报告
```

**关键借鉴点**：
1. **链式配置**：先创建引擎，再逐步添加组件
2. **数据/策略/分析器分离**：清晰的责任划分
3. **运行后统一输出**：所有分析器的结果集中获取

### 3.3 从 QuantConnect LEAN 借鉴：多模式运行

QuantConnect 支持云端和本地双模式，启发我们的三种运行模式：

| 模式 | QuantConnect | 我们的系统 |
|------|-------------|-----------|
| 云端回测 | ✅ 免费额度 | ❌ 不自建云端（成本） |
| 本地回测 | ✅ LEAN 引擎 | ✅ **BACKTEST 模式** |
| 模拟盘 | ✅ 仿真交易 | ✅ **PAPER 模式** |
| 实盘 | ✅ 需 broker | ✅ **LIVE 模式** |

**关键借鉴点**：
1. 同一套策略代码，切换模式只需改配置
2. 回测 → 模拟 → 实盘是自然的演进路径
3. 每种模式有不同的数据流和执行器

### 3.4 从 QMT / PTrade 借鉴：券商接口实践

| 实践 | QMT | PTrade | 我们的设计 |
|------|-----|--------|-----------|
| 运行方式 | 本地 | 云端托管 | **支持切换**（本地优先） |
| 策略安全 | 高（不上传） | 中（放服务器） | **本地运行，策略不上传** |
| 第三方库 | 支持 | 不支持 | **支持**（pip install） |
| 回测周期 | 自定义 | 标准 | **可配置** |
| 品种覆盖 | 股票/期货/期权/ETF/可转债 | 股票为主 | **股票/ETF/可转债**（纯多头） |
| 订单类型 | 标准+算法 | 标准 | **标准+条件单+止损止盈** |

**关键借鉴点**：
1. **本地优先**：策略保密性最重要（参考 QMT）
2. **券商直连**：减少中间环节（参考 QMT/PTrade）
3. **持仓同步时滞补偿**：PTrade 有 6 秒时滞，我们的系统必须处理

### 3.5 从 NinjaTrader 借鉴：回测精度

NinjaTrader 的 tick 级回测是行业标准：

| 精度级别 | NinjaTrader | 我们的系统 | 适用场景 |
|----------|------------|-----------|----------|
| Tick 级 | ✅ 核心功能 | ❌ 不实现（非高频） | 高频/日内 |
| 分钟级 | ✅ | ✅ **默认级别** | 日频/分钟频策略 |
| K 线级 | ✅ | ✅ 快速验证 | 粗略估算 |

**关键借鉴点**：
1. 回测精度可配置（tick / 分钟 / K 线）
2. 高精度回测慢但准，低精度回测快但糙
3. 我们的系统以分钟级为默认，K 线级为快速验证

### 3.6 从 VectorBT 借鉴：向量化加速

VectorBT 的核心思想：用 NumPy/Numba 批量计算，替代逐条循环。

**我们的实现（polars 版）**：

```python
# 传统事件驱动（Backtrader 风格）- 慢但灵活
for bar in bars:
    for obj in objects:
        signal = obj.calculate(bar)  # 逐条计算
    
# 向量化加速（VectorBT 风格）- 快但简化
# 用 polars 对整个 DataFrame 计算
signals = df.with_columns([
    volfac.calculate_vectorized().alias("volfac_signal"),
    tkr7.calculate_vectorized().alias("tkr7_signal"),
])

# 我们的策略：混合模式
# - 对象卡内部：尽可能向量化（polars）
# - 跨对象卡协调：事件驱动（保证灵活性）
# - 回测执行：事件驱动（保证精度）
```

**关键借鉴点**：
1. **对象卡内部向量化**：每个对象卡的 `calculate()` 用 polars 实现
2. **Pipeline 事件驱动**：对象卡之间的调度用事件驱动
3. **关键路径加速**：数据加载、特征计算用向量化

## 四、我们系统的差异化定位

### 4.1 与现有平台的根本区别

```
┌────────────────────────────────────────────────────────────────────┐
│                    我们系统的独特定位                               │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│  不是又一个 Backtrader / vn.py 复刻                                │
│  不是又一个 QMT / PTrade 封装                                      │
│  不是又一个聚宽 / 米筐 云端平台                                    │
│                                                                    │
│  我们的核心差异：                                                   │
│                                                                    │
│  1. 【对象卡驱动】每个指标/策略是一个独立"对象卡"，                  │
│     有统一接口、成熟度、互锁机制。不是传统"策略类"。                │
│                                                                    │
│  2. 【三层决策】PeriodQueen → StrategyBundles → Vote+Risk          │
│     环境识别 → 策略选择 → 执行管理，不是单一策略运行。              │
│                                                                    │
│  3. 【明朝内阁治理】五态动态切换（常态/牛市/熊市/震荡/危机）        │
│     策略、风控、仓位随市场环境自动调整。                            │
│                                                                    │
│  4. 【回测诚实性优先】滑点/延迟/流动性从回测阶段就引入              │
│     不是"回测好看、实盘崩盘"。                                     │
│                                                                    │
│  5. 【技术面+基本面+风控三权分立】类似法院/警察局/立法会           │
│     不是单一信号驱动，是多维度制衡。                                │
│                                                                    │
│  6. 【纯本地化】策略不上传云端，Windows 单机运行                    │
│     不是 SaaS，是个人资产管理工具。                                 │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

## 五、关键设计决策（基于对比）

### 5.1 架构决策

| 决策 | 选择 | 对比参考 | 理由 |
|------|------|----------|------|
| 核心架构 | **事件驱动 + 向量化混合** | Backtrader(纯事件) vs VectorBT(纯向量) | 灵活性 + 性能平衡 |
| 数据处理 | **polars 优先** | pandas(慢) vs polars(快) | 性能优先 |
| 券商接口 | **统一抽象 + 插件化** | vn.py Gateway 模式 | 切换券商零成本 |
| 运行模式 | **BACKTEST / PAPER / LIVE** | QuantConnect 双模式 | 自然演进路径 |
| 策略存储 | **本地文件 + Git 版本控制** | 聚宽(云端) vs QMT(本地) | 保密 + 版本管理 |
| 配置文件 | **Python dataclass + JSON** | QMT(专有格式) | 可读 + 可编程 |

### 5.2 回测决策

| 决策 | 选择 | 对比参考 | 理由 |
|------|------|----------|------|
| 默认精度 | **分钟级** | NinjaTrader(tick) vs 聚宽(日级) | A 股日频/分钟频策略 |
| 快速验证 | **K 线级 + 固定滑点** | Backtrader | 快速筛选 |
| 深度回测 | **分钟级 + 自适应滑点 + 延迟** | NinjaTrader | 接近实盘 |
| 撮合机制 | **当日信号 → 次日开盘成交**（默认可改） | 聚宽/米筐差异 | T+1 约束 |
| 费用模型 | **完整 A 股费用** | 各平台简化 | 万 2.5 + 千 1 + 过户费 |

### 5.3 实盘决策

| 决策 | 选择 | 对比参考 | 理由 |
|------|------|----------|------|
| 券商支持 | **Ptrade / QMT 优先** | 掘金/迅投/恒生 | 国内主流 |
| 订单类型 | **TARGET_VALUE / TARGET_AMOUNT / LIMIT** | Ptrade API | 与券商 API 对齐 |
| 风控前置 | **独立异步检查** | 各平台内置 | 不阻塞主路径 |
| 监控告警 | **五层 + Windows 弹窗** | 各平台差异 | Windows 环境 |
| 灾难恢复 | **WAL + 快照 + 自动重启** | 机构级系统 | 最小可行 |

## 六、各平台撮合机制对我们回测设计的启示

来源：[知乎 - 自己如何做量化交易](https://zhuanlan.zhihu.com/p/386590585)

| 平台 | 撮合规则 | 对我们回测的影响 |
|------|----------|------------------|
| 聚宽 | 当日下单，当日成交，当日开盘价 | **最乐观假设**，我们不用 |
| 米筐 | 当日下单，当日成交，次日开盘价或当日收盘价 | **较乐观**，我们不用 |
| BigQuant | 当日下单，次日成交，次日开盘价 | **T+1 保守**，我们默认用 |
| 优矿 | 当日下单，当日成交，次日开盘价 | 混合规则，不一致 |

**我们的回测撮合规则**：

```python
class BacktestExecutionConfig:
    """回测执行配置，明确记录所有假设。"""
    
    # 撮合规则（默认 T+1 保守）
    fill_timing: str = "next_bar_open"  # 信号 bar 的下一根开盘成交
    
    # 滑点模型
    slippage_model: str = "adaptive"    # adaptive / fixed / random
    slippage_fixed_pct: float = 0.001   # 固定 0.1%
    
    # 按市值分档的滑点
    slippage_tiers: dict = {
        "large_cap": 0.0005,    # 大盘蓝筹
        "mid_cap": 0.001,       # 中盘
        "small_cap": 0.002,     # 小盘
        "micro_cap": 0.003,     # 微盘
    }
    
    # 延迟模型
    signal_delay_ms: float = 0.0        # BACKTEST=0, PAPER=1000, LIVE=3000
    
    # 费用模型（完整 A 股）
    commission_rate: float = 0.00025    # 万 2.5
    stamp_tax_rate: float = 0.001       # 千 1（仅卖出）
    transfer_fee_rate: float = 0.00002  # 十万分之 2
    min_commission: float = 5.0         # 最低 5 元
    
    # 流动性模型
    vwap_threshold_pct: float = 0.10    # 超过 1 分钟成交额 10% 触发 VWAP
```

> **核心原则**：回测不是证明策略好，而是证明策略不坏。所有乐观假设都要标注，所有费用都要计入。

## 七、框架选择决策树（给用户的建议）

如果用户问"我应该用哪个平台？"，这是建议：

```
你有编程能力吗?
│
├─ 没有编程能力
│   └─ 用 果仁 / BigQuant 可视化（但注意黑箱风险）
│
├─ 有基础 Python
│   ├─ 只想快速验证想法 → 用 聚宽/米筐（研究用）
│   ├─ 想做实盘但不想自建 → 用 QMT / PTrade（券商提供）
```
