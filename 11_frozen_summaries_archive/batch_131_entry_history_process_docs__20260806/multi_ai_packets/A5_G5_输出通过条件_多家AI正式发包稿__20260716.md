# A5 G5 输出通过条件 多家AI正式发包稿

更新时间：2026-07-16

## 用途

- 这份发包稿只负责把 `A5 / G5` 当前“输出通过条件”讨论，压成可直接复制发送的标准文本。
- 当前不是开放式闲聊。
- 当前是：
  - 可发包
  - 可回收
  - 可裁决

## 使用方式

- 发给外部模型时，不要自由改写核心边界。
- 若需要差异化提问：
  - 只改“视角偏置”
  - 不改 `TASK / BACKGROUND / KNOWN_CONSTRAINTS / DISCUSSION_SCOPE`
- 默认至少发给 `3` 类视角：
  - 架构/系统
  - 执行/落地
  - 风险/反例

## 标准发包稿

```text
你现在参与的是一个多AI讨论，不是自由闲聊。

TASK:
- 讨论 A5 当前 G5 三个组合层输出段（target_weight / portfolio_tracking_error / adjusted_position_weight）何时才允许从 output_closure_under_judgement__not_closed 升格为 output_passable，并给出 2-4 个不同方案对照。

BACKGROUND:
- 当前 G5 五段主链已经推进到：
  - alpha_score = contract_frozen_proxy
  - covariance_model_id = future_only_but_under_judgement
  - target_weight = output_closure_under_judgement__not_closed
  - portfolio_tracking_error = output_closure_under_judgement__not_closed
  - adjusted_position_weight = output_closure_under_judgement__not_closed
- 当前已经完成的不是：
  - 组合层实现
- 当前已经完成的是：
  - 主链端到端可读
  - 三个输出段全部进入输出闭合判断层
- 当前真正卡住的不是链条结构，而是缺少“什么叫通过”的统一裁决口径

KNOWN_CONSTRAINTS:
- 当前阶段仍禁止：
  - runtime 新开发
  - 默认执行逻辑扩展
  - 回测自动化
  - second-hop 大范围深扫
- 不允许把：
  - under_judgement
  - proxy
  - future_only
  误写成：
  - ready
  - output_closed
  - implementation_ready
- 不允许为了推进感，直接宣布任一输出通过
- 不允许把降级模式输出写成完整优化器正式输出
- 若缺证据，必须显式写 NEED_EVIDENCE

CURRENT BLOCKERS:
- target_weight = output_closure_under_judgement__not_closed
- portfolio_tracking_error = output_closure_under_judgement__not_closed
- adjusted_position_weight = output_closure_under_judgement__not_closed
- covariance_model_id = future_only_but_under_judgement

DISCUSSION_SCOPE:
- 本轮允许讨论：
  - target_weight 何时算通过
  - portfolio_tracking_error 何时算通过
  - adjusted_position_weight 何时算通过
  - 三者的先后顺序
  - 哪些条件必须满足才可升格
  - 哪些条件缺失时必须继续写 not_closed
- 本轮不要展开：
  - 代码实现
  - 优化器求解器选型
  - 分钟/Level-2 解冻
  - 新资料补采
  - 新系统扩张

FREE_GUESS_RANGE:
- 允许合理推测：
  - 哪个输出最适合先过“通过门槛”
  - 哪些通过条件可以先冻结为合同层真值
  - 哪些条件必须保留 NEED_EVIDENCE
- 以下内容若无硬证据必须写 NEED_EVIDENCE：
  - covariance_model_id 已 ready
  - target_weight 已有正式优化器输出
  - portfolio_tracking_error 已有正式 benchmark 风险输出
  - adjusted_position_weight 已可直接运行

CANDIDATE MODES:
1. 最严通过型
- 三个输出都不允许先过
- 直到 covariance_model_id + target_weight 都有更强闭合证据

2. 单段先过型
- 只允许 target_weight 先定义最小通过条件
- 其余两个继续保留 not_closed

3. 双段联动型
- target_weight + portfolio_tracking_error 联动定义通过条件
- adjusted_position_weight 继续保留到最后

4. 全段条件冻结型
- 三段都先冻结“通过条件”
- 但三段都不直接宣布通过

EXPECTED_OUTPUT:
- 请至少给出 2-4 个不同方案，不允许只给唯一答案
- 每个方案至少说明：
  - 方案名
  - 核心思路
  - 适用条件
  - 优点
  - 缺点
  - 风险
  - NEED_EVIDENCE
  - 为什么适合当前项目
- 最后必须补：
  - 你最推荐的方案
  - 不推荐其它方案的原因
  - 当前最小下一步

OUTPUT CONTRACT:
1. 结论摘要
2. 方案对比（至少2个）
3. 最推荐方案
4. 当前最小下一步
```

## 视角偏置版

### 架构/系统视角

```text
额外要求：
- 请优先从合同层、对象卡、输出状态升格条件来判断。
- 请回答：哪种方案最不容易把 under_judgement 误写成通过。
```

### 执行/落地视角

```text
额外要求：
- 请优先从清障顺序、返工概率、最小落地成本来判断。
- 请回答：哪种方案最容易形成“可继续推进但不越界”的最小下一步。
```

### 风险/反例视角

```text
额外要求：
- 请优先从失败代价、误写风险、假通过风险来判断。
- 请回答：如果现在选错，哪种路径最容易把 G5 误推进成 output_passable 幻觉。
```

### 规划/排序视角

```text
额外要求：
- 请优先从阶段顺序和后续主线稳定性来判断。
- 请回答：三个输出段的最稳排序是什么，为什么。
```

## 默认发包顺序

- 第 1 轮：
  - 发给 `架构/系统视角`
  - 发给 `执行/落地视角`
  - 发给 `风险/反例视角`
- 第 2 轮：
  - 若分歧明显，再加发 `规划/排序视角`
