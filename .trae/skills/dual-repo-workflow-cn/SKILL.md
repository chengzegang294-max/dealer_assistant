# Dual Repo Workflow (CN)

## 目标

- 固定 `D:\Stock\dealer_assistant` 与 `D:\Stock\trading_assistant` 的分工。
- 防止命令、改动、提交、回链写到错误仓库。
- 约束“旧仓先试/先讨论/先清尾巴，新仓只收正式结果”的工作流。
- 明确哪些内容应该平移到新仓，哪些内容继续留在旧仓。

## 何时调用

当出现任一情况时，优先调用本 skill：

- 需要在 `dealer_assistant` 与 `trading_assistant` 之间决定工作落点
- 需要判断某份文档、runtime、脚本、测试结果应留在哪个仓
- 需要从旧仓向新仓吸收“结果明确”的一批内容
- 需要清理旧仓尾巴，但又不想误删还要追溯的内容
- 需要提交、推送、回填 README / 入口页，且担心打错仓
- 用户提到：
  - `新仓 / 旧仓`
  - `主仓 / 老仓`
  - `双仓`
  - `吸收`
  - `切工作目录`

## 仓库角色冻结

### 1. 新仓：`D:\Stock\dealer_assistant`

定位：

- 正式主仓
- 正式主线
- 长期保留的有用成果仓

默认承载：

- 正式文档
- 已收口的 runtime 结果
- 已确认要长期保留的工具和代码
- 会进入 git 历史的正式提交
- 对外同步时应优先引用的入口页和结果页

默认动作：

- 默认工作目录优先指向这里
- 默认提交、推送、README 回填优先落这里

### 2. 旧仓：`D:\Stock\trading_assistant`

定位：

- 操作仓
- 缓冲仓
- 参考仓

默认承载：

- 测试
- 草稿讨论
- 多 AI 发包和待裁决材料
- 暂存吸收线
- scratch / paste zone / 临时中转
- 老材料回看与分批清尾

默认动作：

- 可以继续改
- 不是只读
- 但不再视为正式主线

## 第一原则

- 默认在新仓工作。
- 旧仓继续可改，但只在“有明确理由”时回去改。
- 不做全量平移。
- 不把旧仓里的讨论态、临时态、待裁决内容直接抬进新仓。
- 新仓只吸收“结果明确、用途清晰、值得长期保留”的内容。

## 默认分工规则

### 1. 什么内容默认落新仓

- 正式入口页
- 正式裁决页
- 已验证可复用的 runtime 结果
- 已收口脚本 / 工具增强
- 已经能独立成一个清晰提交的内容

### 2. 什么内容默认留旧仓

- 临时测试
- 待裁决文档
- 多 AI 发包稿 / 回收中间态
- scratch / 粘贴区 / review 参考
- 暂时存放的原始大包
- 还没形成独立结论的实验结果

### 3. 什么内容可以从旧仓吸到新仓

必须同时满足：

- 已形成明确结论
- 已有稳定路径和用途说明
- 不再依赖临时目录才成立
- 不只是一次性会话中转
- 能单独成为 themed commit

若缺任何一项：

- 默认继续留旧仓

## 回旧仓的合法场景

只有以下场景，才默认切回 `D:\Stock\trading_assistant`：

1. 清老尾巴
2. 查看或整理历史上下文
3. 暂存区 / scratch 区收口
4. 试验、讨论、待裁决材料继续推进
5. 从旧仓筛选下一批“结果明确”的吸收物

除此之外：

- 默认不要把工作重心拉回旧仓

## 吸收规则

旧仓 -> 新仓 时，按以下顺序：

1. 先盘点旧仓改动
2. 按：
   - 正式文档
   - runtime 结果
   - 临时区
   - scratch
   分组
3. 只筛出“结果明确”的那一小批
4. 并入新仓
5. 在新仓形成独立提交
6. 再回头处理旧仓剩余尾巴

禁止：

- 一次性全量迁仓
- 把旧仓整个目录直接当新仓覆盖源
- 不分组就大批搬运
- 把旧仓较旧版本反向覆盖新仓较新版本

## 提交与命令规则

### 1. 提交前必须先确认目标仓

每次提交前先明确：

- 当前仓是新仓还是旧仓
- 这次提交是否属于正式主线

若属于正式主线：

- 默认提交到 `dealer_assistant`

若属于试验/讨论/缓冲：

- 默认留在旧仓，不急着提交到新仓

### 2. 推送规则

- 默认只从新仓推送正式主线
- 旧仓不是默认推送仓

### 3. 命令执行规则

凡是可能改文件、跑 git、生成结果时，先判断：

- 这条命令是在为正式主线服务，还是为缓冲/试验服务

判断不清时：

- 优先停在旧仓做判断
- 不直接把不确定的东西落进新仓

## 旧仓尾巴处理规则

旧仓中的以下内容，优先视为尾巴区：

- `暂时存放/`
- `scratch/`
- `from_temp_staging__*`
- 临时 review / paste zone

处理顺序：

1. 先判断是否仍需追溯
2. 若仍需追溯但不该占视野：
   - 优先用 `.git/info/exclude` 隐藏
3. 若已被正式吸收且不再需要：
   - 再删除实体
4. 若仍在被正式文档回链：
   - 先修正文档状态，再删实体

## 执行清单

每次跨仓工作前，先过这 6 句：

1. 当前这步是正式主线，还是缓冲/试验？
2. 当前默认应该落新仓还是旧仓？
3. 这个结果是否已经“明确到可以独立提交”？
4. 这份材料是否仍依赖临时路径才能成立？
5. 这次操作会不会把旧仓较旧内容反向覆盖到新仓？
6. 提交和推送目标仓是否已明确？

若答案是：

- `正式主线 + 已明确 + 不依赖临时路径`
  - 进新仓
- `试验 / 待裁决 / 临时中转`
  - 留旧仓

## 主负责人默认口径

- 当前主线：新仓承接正式成果，旧仓继续做缓冲和清尾
- 当前不是：全量迁仓、双仓并列主线、把旧仓重新当正式主仓
- 当前最值钱一步：把旧仓中“结果明确”的内容小批量吸到新仓
- 暂缓什么：未裁决材料、scratch、中转大包的正式入新仓

## 红线

- 不把两个仓都当正式主线
- 不把旧仓默认当提交和推送仓
- 不把待裁决内容直接塞进新仓
- 不把临时路径长期挂在正式入口文档里
- 不做未经筛选的整仓平移
- 不在未确认目标仓时直接跑提交或推送
